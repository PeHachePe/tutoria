# Paso 2.3 · Ejecución real: Edge Function `execute`

10/11/2026 · Sesión de Claude Code · Commits `c034943` (base de datos), `69da5fc` (código) y `db19b75` (documentación)

## Objetivo

Ejecutar de verdad las pruebas de un intento contra Supabase local:

- una Edge Function `execute` que compruebe la sesión, ejecute el código aislado, compare fuera del sandbox, fije `tests_failed` o `passed` y registre `run`;
- la versión con Supabase de `CodeRunnerService`, para que en `start:local` se pueda resolver y entregar.

## Qué se pidió

- Empezar el paso 2.3.
- El autor recordó que nada está cerrado y que toda mejora es bienvenida, siempre con las buenas prácticas de Angular.
- Ante el plan con Judge0 alojado, preguntó dos veces si no había alternativas más libres, y después cuál era la mejor siendo objetivo.
- Preguntó si un bucle infinito u otros abusos serían un problema con QuickJS.
- Aprobó QuickJS «de momento», preparado para pasar fácilmente a Judge0 en el futuro.

## Problemas y cómo se resolvieron

- **El Edge Runtime no resuelve importaciones sin extensión,** y construye el grafo también con las de tipos: `build-run-result.ts`, que importaba tipos de `attempt.ts`, no arrancaba. Lo compartido con la función es un solo fichero sin importaciones, y `attempt.ts` reexporta sus tipos.
- **Recursión infinita:** con 512 KB de pila, QuickJS desbordaba la pila del propio Edge Runtime (`RangeError` del host) antes de su límite. Con 256 KB, QuickJS da su `stack overflow`, que se muestra como en el navegador. Por si acaso, si el motor falla se vuelve a cargar.
- **El trigger del código:** una ejecución que repetía el estado anterior con código nuevo (de `tests_failed` a `tests_failed`) volvía a `in_progress`, porque en una sola actualización el trigger no distingue la ejecución de una edición. `record_run` guarda primero el código y después el estado, y un test de pgTAP lo cubre.
- **El ejercicio 3 del seed estaba entregado** para el alumno de la primera prueba con `curl`: la función respondió 409, que es lo correcto. Se probó con otro alumno.
- **Un 400 en la consola** al abrir la app: era la renovación de una sesión del navegador anterior al `db:reset`, no algo de este paso.

## Para la presentación

El código del alumnado se ejecuta en un intérprete de JavaScript compilado a WebAssembly, dentro de la propia función del servidor. Sin cuentas, cuotas ni terceros, y el código nunca sale de Supabase. Un bucle infinito se corta en un cuarto de segundo, una bomba de memoria se queda en 32 MB, y los valores esperados de las pruebas nunca llegan a donde corre el código.
