# Paso 2.1 · Supabase local: esquema, RLS y datos

10/11/2026 · Sesión de Claude Code · Commit propuesto: `feat(db): local Supabase schema, row level security and seed (step 2.1)`

## Objetivo

Primer paso del back-end real: la base de datos de Supabase en local, con las tablas de §2.3, la seguridad por fila, las transiciones del intento (§2.4), el seed generado desde las fixtures, los tipos de TypeScript y los tests de las políticas con pgTAP.

## Qué se pidió

- Empezar la fase 2.
- Antes del visto bueno, el autor preguntó:
  - para qué hace falta Docker y si se podía trabajar directamente en la nube;
  - qué eran las contraseñas de demostración, Studio y Mailpit;
  - si convenía Prisma;
  - si sería fácil pasar a producción, qué Edge Functions hacen falta y si Supabase es mejor que un back-end propio.
- Incluir la columna del aviso de datos (RF-07). Preguntó si tenía sentido retirar el consentimiento o borrar la cuenta, y después objetó que retirarlo haría perder la señal de foco y pegado.

## Qué hizo Claude

1. Leyó el paso, §2.3–2.5, §2.8, §2.10, §4.8 y las filas de `PENDIENTES.md` para la fase 2. Respondió a las preguntas:
   - en local, Supabase solo funciona con Docker;
   - la nube es viable, pero con peor ciclo de trabajo y sin probar las Edge Functions en el Mac;
   - Prisma no tiene sentido con la RLS y un cliente que habla directamente con PostgREST;
   - se necesitan tres Edge Functions: `execute`, `tutor` y `admin-users`.
2. `supabase init`, con el registro público desactivado. Otro proyecto de Supabase del Mac ocupaba los puertos por defecto: en lugar de pararlo, TutorIA pasa a los 553xx.
3. Cuatro migraciones:
   - **tablas:** los tipos, las 11 tablas con `kind`, `received_at` y `privacy_notice_seen_at`, y las reglas de borrado del simulado;
   - **seguridad:** privilegios desde cero, nueve funciones auxiliares y RLS en todas las tablas;
   - **transiciones:** el trigger del código, `open_attempt` y `submit_attempt`;
   - **alta de usuarios:** el trigger que crea `app_user` como `student`.
4. El generador del seed escribe antes las cuentas de `auth.users` (con su identidad de correo, la contraseña de prueba y las desactivadas bloqueadas) y pasa `app_user` a `on conflict do update` (D-018). Se escribieron primero sus tests.
5. Comprobó con la API de Auth que una alumna entra, que el usuario desactivado queda bloqueado y que el registro está cerrado.
6. 59 tests de pgTAP en cinco ficheros: los cuatro del plan, las filas de seguridad del 1.6 (desentregar, `open_attempt` duplicado y `process_event` solo para insertar), el docente, el administrador y el alta de usuarios.
7. Tipos con `npm run db:types`; scripts `db:start`, `db:stop`, `db:reset`, `db:test` y `db:types`.
8. Por la objeción del autor, quitó la columna de retirada del consentimiento que había añadido: el registro forma parte de la función educativa y el aviso informa (D-040).

## Problemas y cómo se resolvieron

- Docker estaba cerrado y después a medio arrancar (`Internal Server Error`): el autor lo abrió.
- `supabase migration new` dio a las cuatro migraciones la misma marca de tiempo. Se habrían aplicado en orden alfabético y con versiones repetidas: se renombraron en secuencia.
- Los puertos 543xx los usaba otro proyecto (`guinyote-supabase`): TutorIA usa los 553xx.
- Cuatro nombres de política pasaban de 63 caracteres y Postgres los truncaba: se acortaron.
- Con `enable_signup = false` en `[auth.email]`, Auth desactiva todo el proveedor de correo («Email logins are disabled»). Se dejó activado ahí: basta con el `[auth]` general. Los cambios de Auth no se aplican con `db reset`, sino con `supabase stop` y `start`.
- El fichero de tipos generado no cumple dos reglas de estilo de ESLint: se excluye del lint y de la cobertura, como código generado (D-010), sin tocar las reglas.
